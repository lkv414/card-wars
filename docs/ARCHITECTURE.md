# Архитектура (высокоуровневая)

## Главная идея

Игра строится как **чистый игровой движок + тонкие адаптеры**.

```
┌─────────────────────────────────────────────────────┐
│                    Presentation                      │
│              (3D UI, ввод пользователя)              │
└──────────────────────┬──────────────────────────────┘
                       │ команды / события
┌──────────────────────▼──────────────────────────────┐
│                  Application                         │
│     (use-cases: начать матч, сыграть карту,          │
│      закончить ход, сохранить реплей…)               │
└──────────────────────┬──────────────────────────────┘
                       │
┌──────────────────────▼──────────────────────────────┐
│                     Domain                           │
│  • Модели (Card, Player, Zone, Match…)               │
│  • Правила и валидация                               │
│  • State machine хода                                │
│  • Применение эффектов и способностей               │
│  • Чистые функции перехода состояния                 │
└─────────────────────────────────────────────────────┘
                       ▲
                       │ порты
┌──────────────────────┴──────────────────────────────┐
│                   Adapters                           │
│  • Persistence (колоды, реплеи)                      │
│  • Multiplayer transport                             │
│  • Clock / RNG                                       │
└─────────────────────────────────────────────────────┘
```

Domain **ничего не знает** о конкретном UI-фреймворке, 3D-движке, базе данных или транспорте сети.

---

## Слои подробнее

### 1. Domain (ядро)

Ответственность:
- Описание всех игровых сущностей.
- Валидация действий («можно ли сейчас сыграть эту карту»).
- Переходы состояния матча.
- Расчёт урона, флюпов, пассивных способностей, замен, розыгрыша карт.
- Логика 2–4 игроков и смены ближайших противников.
- Определение победителя / выбывания.

Характеристики:
- Чистые функции или методы без побочных эффектов (кроме явно переданного RNG).
- Полностью покрыто unit-тестами.
- Не зависит от интерфейса и сети.

### 2. Application

Оркестрирует сценарии:
- «Создать новый матч на N игроков»
- «Игрок хочет сыграть карту»
- «Игрок заканчивает ход»
- «Игрок выбыл — перестроить ближайших противников»

Не содержит правил «как считается урон», только вызывает domain.

### 3. Presentation

- Отображает текущее состояние матча в **3D**.
- Собирает намерения пользователя и передаёт их в application в виде команд.
- Не решает, законно ли действие.

### 4. Adapters

Всё, что касается внешнего мира:
- Загрузка/сохранение колод.
- Мультиплеер (когда появится).
- Генерация случайных чисел (чтобы тесты были детерминированными).
- Логирование и т.п.

---

## Состояние матча

Состояние — **единый иммутабельный снимок**.

Любое действие игрока = команда → domain проверяет → возвращает новый снимок (или ошибку).

Рекомендуемый подход к ходу — **явный state machine** фаз, например:

```
Setup → Draw → Main (действия / флюпы) → Combat → EndTurn → (следующий игрок)
```

Конкретные названия фаз будут уточнены. Важно, чтобы фаза была частью состояния и ограничивала доступные команды.

---

## Карты и эффекты

Карты описываются данными (id, тип, стоимость, требования к землям, атака/защита, способности).

Эффекты и способности реализуются как:
- декларативные операции (нанести N урона, добрать карту, уничтожить…),
- либо именованные обработчики для сложных случаев.

UI не должен содержать логику «что делает эта карта».

---

## Чего намеренно избегаем

- Игровой state, размазанный по UI-компонентам.
- 3D-сцена как часть ядра правил.
- Сложная сетевая синхронизация на самых ранних этапах.
- Привязка правил к конкретной базе данных или realtime-каналу.
- Монолитный store, который одновременно знает про сеть, UI и правила.

---

## Эволюция

1. Domain + тесты + минимальный способ проверить правила.
2. Полноценный 3D-интерфейс.
3. Сохранение колод, реплеи.
4. Мультиплеер как адаптер.
