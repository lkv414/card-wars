# Архитектурный отчёт: Hearthstone vs Card Wars v3

- **Дата:** 2026-11-03
- **Ветка репозитория:** `v3` (рабочее дерево с незакоммиченными изменениями механик M3 — все номера строк даны по нему)
- **Автор:** исследовательская сессия ZCode (аудит кода репозитория + исследование открытых источников по Hearthstone)
- **Назначение:** полный отчёт для передачи другому агенту для независимого анализа с его собственным контекстом. Ничего из этого отчёта не реализовано в коде — это исследование и рекомендации.
- **Маркировка достоверности:** факты о Card Wars подтверждены чтением кода (указаны `файл:строка`). Факты о Hearthstone — из реверс-инжиниринга: `[A]` = подтверждается несколькими независимыми источниками, `[B]` = один источник / реконструкция по описаниям.

---

## TL;DR

1. Скелетно Card Wars v3 и Hearthstone **уже совпадают**: обе системы разделяют *определение карты* (статические данные) и *игровой инстанс* (мутабельное состояние в матче), сервер авторитарен, клиент — тонкий рендерер, данные карт не зашиты в код правил.
2. Ключевое отличие Hearthstone: **всё — сущности с мешком тегов** (даже стоимость, зона, флаги статусов), **баффы/ауры — тоже сущности** (зачарования), а **состояние реплицируется потоком элементарных дельт** (`TAG_CHANGE` и т.п.), который же служит логом/реплеем.
3. Ключевое отличие Card Wars: типизированные поля вместо тегов, ауры пересчитываются в точке использования (не материализуются), баффы не имеют идентичности (нет id/источника), синхронизация — полные персональные снапшоты + события только для анимаций.
4. Рекомендуется заимствовать: теги-статусы на инстансе, идентичность баффов (источник + id), атомарные события презентации, требования розыгрыша как данные. Не рекомендуется: мешок тегов на всё, спецкод на карту, потоковые дельты вместо снапшотов.
5. Попутная находка: `docs/CARDS.md` устарел относительно кода (см. §4.7).

## 1. Контекст исходного запроса

Вопрос пользователя (воспроизведён по смыслу): «Есть ли известная архитектура Hearthstone? Сравни её с нашей игрой. Особенно интересует, как берутся карты: у нас вроде как карта — отдельный объект, грубо говоря, 1 карта — это 1 файл с данными, и игра берёт данные оттуда. Правильно ли я понимаю устройство нашего кода? В чём отличия и что мы могли бы позаимствовать?»

Короткий ответ: понимание **верно с одной поправкой**. Карта в Card Wars — это действительно данные (не код), но в коде уже есть важное разделение: файл в `content/` описывает *определение* карты, а в матче каждая копия карты — отдельный *инстанс* (`CardInstance`) со своим `instanceId` и мутабельным состоянием, который ссылается на определение по `cardId`. Это тот же принцип definition/instance, что и в Hearthstone. Различия лежат в модели баффов, статусных флагов и способе репликации состояния (детали в §5–6).

## 2. Методология и ограничения

- **Исходники Hearthstone закрыты.** Знания получены из четырёх типов источников: (1) распарсенные файлы данных клиента — `CardDefs.xml` / DBF; (2) сетевые логи и формат PowerHistory/PowerLog; (3) независимые пере-реализации движка проектом HearthSim (`python-hearthstone`, симулятор `fireplace`); (4) обобщения сообщества (`awesome-hearthstone`, HearthDb, HearthstoneJSON). Все ссылки — в §8.
- **Card Wars v3 — открытый код этого репозитория.** Аудит выполнен 2026-11-03 по рабочему дереву ветки `v3` (незакоммиченные изменения M3 учтены).
- В репозитории действует **clean-room политика**: Hearthstone в проекте ни на что не ссылается и не должен ссылаться. Настоящий отчёт — внешнее исследование для архитектурного сопоставления, не источник правил игры. Из HS заимствуются *идеи*, не контент.
- Оценки «лучше/хуже» даны относительно целевых ограничений Card Wars: 2–4 игрока, 544 карты, Cloudflare Workers + Durable Objects, TypeScript strict, чистый domain.

## 3. Архитектура Hearthstone (по данным реверс-инжиниринга)

### 3.1 Общая топология `[A]`

- Клиент — Unity (C#); сервер — авторитарный C#-бэкенд Blizzard. Клиент не принимает решений о легальности действий: он рендерит состояние, шлёт намерения и воспроизводит поток изменений.
- Всё игровое состояние — множество **сущностей (Entity)**: каждый экземпляр карты в матче, а также игрок и сам матч — сущности.
- Сущность = числовой уникальный ID (в пределах матча) + **словарь тегов `GameTag → значение`**. Теги — целочисленные энумы: атака, здоровье, стоимость, зона, булевы флаги (Taunt, Divine Shield, Frozen...), счётчики.
- **Зона — тоже тег** (`ZONE`: HAND/DECK/PLAY/GRAVEYARD/SETASIDE); при этом сущности физически лежат в списках зон контроллера (в fireplace: `_set_zone` вынимает из кеша старой зоны и вставляет в новую).

### 3.2 Определение карты: CardDefs / DBF `[A]`

- Статические данные карт хранятся в файлах данных клиента: `CardDefs.xml` (и табличная форма DBF — она используется для обмена колодами, у карт есть DBF ID). Каждая карта — запись с `CardID` (строка, например `CS2_042`) и **стартовым набором тегов**.
- Иллюстрация формата (реконструкция для наглядности, не дословный файл; в реальном файле имена тегов — числа из GameTag-энума, HearthstoneJSON восстанавливает имена):

```xml
<Entity CardID="CS2_042">   <!-- Sen'jin Shieldmasta -->
  <Tag GameTag="CARDTYPE" Value="MINION"/>
  <Tag GameTag="COST" Value="3"/>
  <Tag GameTag="ATK" Value="3"/>
  <Tag GameTag="HEALTH" Value="5"/>
  <Tag GameTag="TAUNT" Value="1"/>
</Entity>
```

- Ключевое следствие: **даже стоимость, атака, здоровье и зона — теги**. Отдельных типизированных полей нет: модель «мешок тегов» универсальна для всего.
- **Зачарования (enchantments) — тоже карты**: в `CardDefs` есть записи с ID вида `CS2_042e`, которые никогда не лежат в колодах, а создаются движком в матче как баффы. То есть у баффа есть собственное определение в данных.

### 3.3 Баффы и ауры — сущности `[A]`

- При наложении баффа движок **создаёт сущность-зачарование**, привязанную к хосту (в fireplace: `buff = source.buff(self, id)`; «на хосте» = `zone == PLAY` + ссылка на `owner`). У зачарования есть CardID, источник, собственные теги, а иногда собственные триггеры и даже «смерть».
- **Итоговые статы не хранятся в инстансе — вычисляются при чтении**: базовый тег карты + вклад всех зачарований и аур. В fireplace это свойство `atk`, которое складывает базу со всеми слотами/баффами (`i += getattr(self, "_" + attr, 0)`); здоровье = `max_health − damage`.
- **Ауры — сущности, которые «тикают»**: периодически пересоздают/обновляют зачарования на своих целях (в fireplace: класс `Refresh`, `AuraBuff`, глобальный список `game.active_aura_buffs`, поле `tick` для защиты от пересоздания уже существующего баффа тем же источником).

### 3.4 Триггеры и обработка смертей `[B]`

- Триггеры («когда X — сделай Y») реализованы как **зачарование-сущность с данными триггера**, висящая на хосте.
- Сервер исполняет действие как **очередь PowerTask'ов**; последовательное исполнение порождает журнал изменений (PowerHistory). Смерти обрабатываются отдельной фазой «Death Processing» после полного разрешения действия (сущности сначала помечаются `to_be_destroyed`, потом умирают пачкой).

### 3.5 Репликация: PowerHistory `[A]`

- Сервер шлёт клиенту **поток элементарных операций**, а не снапшоты:
  - `FULL_ENTITY` — создать сущность с набором тегов;
  - `SHOW_ENTITY` — раскрыть ранее скрытую сущность (передаётся реальный CardID);
  - `HIDE_ENTITY` — скрыть сущность;
  - `TAG_CHANGE` — изменить один тег одной сущности (это основной «кирпич»);
  - `META_DATA` — вспомогательные подсказки для UI.
- Это **один формат для трёх вещей сразу**: живой игры, лога матча и реплеев (Hearthstone Deck Tracker строит на нём всю статистику).
- **Скрытие информации**: карты в руке/колоде оппонента отправляются как скрытые сущности (без CardID); раскрытие происходит в момент розыгрыша через `SHOW_ENTITY`. Клиент в принципе не получает данных, которые ему знать нельзя.

### 3.6 Требования розыгрыша: PlayReq `[B]`

- Легальность розыгрыша описывается **списком требований-данных** (`REQ_TARGET_TO_PLAY`, `REQ_HAND_NOT_FULL`, ...), приложенных к определению карты, а не императивным кодом. В fireplace `is_playable()` — конечный автомат по списку PlayReq из определения.

### 3.7 Границы data-driven подхода `[A]`

- Для сложных карт **Blizzard пишет спецкод в движке по карточному ID** — декларативный слой покрывает не всё. В fireplace логика карт — Python-скрипты per-card (`data.scripts`: события, cost_mod, powered_up, enrage и т.п.).
- Вывод: «чистый data-driven» у реального Hearthstone не достигнут; проект HearthSim воспроизводит это через per-card скрипты. Card Wars идёт дальше в декларативность (§4.4).

## 4. Card Wars v3: фактическая архитектура (аудит кода)

### 4.1 Монорепо и стек

- pnpm workspaces: `packages/{domain,application,protocol,content}` + `apps/{server,client}`; TypeScript strict.
- **domain — чистый**: ноль I/O, единственная зависимость — Immer; никаких `Math.random` — RNG через порт, сид в состоянии матча; zod только на границах (protocol/адаптеры); константы правил — только из CONFIG (`docs/CONFIG.md`); ни одной ссылки на конкретную карту в коде правил (конвенции AGENTS.md).
- Сервер: Cloudflare Workers + Durable Object (класс `Room`), SQLite write-through, alarms, WebSocket (`apps/server/src/room.ts`).
- Клиент: React + Vite + react-three-fiber (3D-поле), DOM — меню/лобби/редактор колод.
- Синхронизация: полные персональные снапшоты `viewFor(state, playerId)` после каждого действия + события только для анимаций/журнала (docs/TECH.md).
- Тесты: Vitest (+ fast-check), сидированный RNG.

### 4.2 Контент-пайплайн (как «берутся» карты)

Исходники двухслойные:

1. `content/cards/json/*.json` (544 файла) — базовая карточка. Поля: `id, name, type` (человекочитаемый текст), `typeCategory` (creature/spell/building/companion), `landType, cost, attack, defense, description, flavor, abilities` (в исходнике пустой), `image, deckSet, sets, sha256, sources`. Пример: `content/cards/json/finn_card_5.json`.
2. `content/cards/mechanics/<cardId>.json` — механики v2 (не для всех карт). Формат: `cardId, name, abilities[]`, где способность — `{kind: passive|active, trigger, effect: {op, target, amount, ...}, text}`. Пример: `content/cards/mechanics/bmo_card_10.json` (`trigger: start_of_turn`, `effect: {op: "discard_top_deck", count: 1}`).
3. `content/index.json` — плоский список `{id, name, deckSet, image, kind}` для поиска/редактора колод; в движке не участвует.

Генератор `tools/build-catalog.mjs`:

- валидирует DSL по фиксированным множествам (`EFFECT_OPS`, `TRIGGERS`, `TARGET_ASKS`, `TARGET_REFS`, `AMOUNT_KINDS`, `CONDITION_KINDS` — строки 67–87);
- мержит `abilities` из слоя механик в карточки (строки 230–237);
- пишет `packages/content/src/generated/cards.json` и `heroes.json`.

Экспорт: `packages/content/src/index.ts:10–19` — `cards`, `heroes` и `catalog: CardCatalog = { getCard, getHero }`.

Т.е. **логика эффекта — чистые данные** (декларативный DSL: `op` + `target` + `amount`, либо ссылка на именованную механику `mechanic + params`); ссылок на функции в JSON нет.

### 4.3 Domain: определение vs инстанс

- **Определение**: `CardData` (`packages/domain/src/types.ts:13–26`) — `id, name, type, cost, landType, attack?, defense?, image?, description?, abilities?: AbilitySpec[], deckSet?`; `HeroData` (28–34).
- **Инстанс**: `CardInstance` (`types.ts:63–79`) — `id` (instanceId вида `` `${playerId}#${i}` ``), `cardId, controller, location, zone, slot, flipped, damage, shield, bonusAttack, bonusDefense, playedTurn`.
- `MatchState.instances: Record<string, CardInstance>` (`types.ts:135`); игрок держит только списки id (`deck/hand/discard: string[]`; `zones: ZoneState {creature, building}` — `types.ts:58–61, 88–90`). Инстансы создаются в `packages/domain/src/match/create.ts:112–128`.
- Определение **не копируется в состояние** — доступ через порт `CardCatalog { getCard, getHero }` (`packages/domain/src/catalog.ts:5–8`), передаваемый в `DomainDeps` (`commands.ts:33–36`) и `Ctx` (`util.ts:16–21`). Хелпер `cardOf(ctx, inst)` (`util.ts:39–43`) бросает `unknown_card`.
- Эффективные статы считаются **в точке использования**: `computeEff` (`packages/domain/src/stats.ts`) — `card.attack + inst.bonusAttack + turnBuffs + вклад аур`.

### 4.4 Механики v2 (`packages/domain/src/mechanics/`)

Типы данных (`mechanics/types.ts`): `Trigger` (10–25), `TargetAsk/TargetChoice` (44–65), `TargetRef` (68–81), `TargetFilter` (86–99), `StatAmount` (102–125; число или `per_discard / per_damage / per_distinct_lands / per_lands / per_target / per_counter`), `ConditionSpec` (132–156; `if_*`/`while_*`), `EffectSpec` (172–202; 15 операций `deal_damage … land_count_mod`), `AbilitySpec` (204–221), `QueuedAbility` (224–233), `PendingChoice` (236–244).

Как поведение рождается из данных:

- **Интерпретатор**: `runEffect` (`mechanics/effects.ts`) — `switch (effect.op)` по данным карты. Аура как активируемая способность запрещена (`aura_not_castable`, `effects.ts:82–84`).
- **Ауры не материализуются в состоянии**: `auraContributions` (`mechanics/modifiers.ts:31–55`) пересчитывает вклад в точке использования; `forSource` (58–88) обходит все зоны/компаньонов/героев и читает `card.abilities` из каталога. Источник ауры в состоянии не персистится.
- **Триггеры**: `enqueueTrigger` (`mechanics/dispatch.ts`) кладёт `QueuedAbility` в `ctx.frame.queue`; способности с выбором цели ставят матч в паузу `MatchState.pending`, продолжение — `resolvePending`; валидация выбора — `validateChoices` (`mechanics/resolve.ts`) атомарно сверяет `TargetChoice` с `TargetAsk`.
- **Хранимые модификаторы в состоянии**: `bonusAttack/bonusDefense` на инстансе (перманентные), `MatchState.turnBuffs: TurnBuff[]` — `{instanceId, stat, amount, grantedOnTurn}` (`types.ts:112–117`, запись в `effects.ts:88–96`), `turnCounters`, `abilityUses`. **У баффов нет собственного id и нет источника.**
- **Именованные механики**: `registry.ts` — `MECHANICS: Record<string, MechanicHandler>` (сейчас пуст), `runMechanic` бросает `mechanic_unknown`. Слой для сложных эффектов, невыразимых в DSL: код *механики*, а не карты — конкретные карты в коде по-прежнему не упоминаются.

### 4.5 Синхронизация и скрытие информации

- `viewFor` — единственное место построения вида (`packages/application/src/view.ts:55`). `cardView` (`view.ts:12–30`) отдаёт `CardView`: `instanceId, cardId, damage, shield, bonusAttack, bonusDefense, flipped, effAttack, effDefense` — **без name/cost/text**.
- Рука оппонента — только `handCount`; `discard`/`myHand` — `{instanceId, cardId}`. Схема — zod в `packages/protocol/src/index.ts:21–30` (`CardViewSchema`).
- **Данные карт клиент берёт сам из каталога**: `apps/client/src/game/scene/Hand.tsx:5`, `apps/client/src/decks.ts:2`. Каталог вшит в бандлы обеих сторон (docs/TECH.md, решение №6 — без БД/KV).
- `pending` в снапшоте — только факт ожидания; `askCount` добирается из каталога (`view.ts:33–48`).
- Скрытая информация не покидает сервер: `viewFor` строит персональный вид; события не содержат скрытых данных (конвенция №4).

### 4.6 Статусы на инстансах

- Универсальных тегов/флагов **нет**. На `CardInstance` — только булево `flipped` (floop) и числовые `damage/shield/bonusAttack/bonusDefense`; у земель — `LandState.frozen/flipped` (`types.ts:52–56`).
- Заморозка существует только для земель (`op: freeze_land` → `land.frozen`, `effects.ts:136–138`); статусных флагов существ (таунт/оглушение и т.п.) нет.
- Условное поведение описывается `ConditionSpec` в данных и пересчитывается при сканах, а не флагами на инстансе.
- Модуль смертей: `packages/domain/src/deaths.ts` (в работе на момент аудита).

### 4.7 Соответствие доков коду

- `docs/CARDS.md` утверждает: «v1-система структурированных способностей удалена, у `CardData` нет поля `abilities`» — **устарело**: `abilities` есть (`types.ts:24`), механики v2 реализованы и мержатся в каталог. Документ требует правки (doc-first конвенция).
- `docs/MECHANICS-V2.md`: гибридная модель — простые способности декларативно в JSON, сложные — именованные механики кодом в domain (реестр без имён карт); связка по `id`; цели одной командой; `pendingChoice` для триггеров; пассивки/ауры пересчитываются в точке использования без мутации состояния. **Соответствует коду.**
- `docs/TECH.md`: TS повсюду, Workers + DO, полный персональный снапшот после каждого действия, события — только для презентации, каталог вшит пакетом `content`. **Соответствует коду.**

## 5. Сравнение

### 5.1 Совпадения по скелету (важно: пользовательское понимание верно)

| Ось | Hearthstone | Card Wars v3 |
|---|---|---|
| Определение карты | запись в CardDefs (теги) | `CardData` из JSON-каталога |
| Игровой инстанс | Entity с уникальным ID | `CardInstance` с `instanceId` |
| Связь инстанс→определение | по CardID | по `cardId` через порт `CardCatalog` |
| Сервер | авторитарный | авторитарный (domain — единственный источник законности) |
| Клиент | тонкий рендерер | тонкий (presentation не решает законность, анимации — по событиям) |
| Данные карт вне кода | да (файлы данных) | да (`packages/content`, запрет хардкода конвенцией №2) |
| Скрытие информации | скрытые сущности в потоке | персональный `viewFor` (проще и надёжнее) |

### 5.2 Ключевые отличия

| Ось | Hearthstone | Card Wars v3 | Оценка |
|---|---|---|---|
| Модель статов | мешок тегов, статы — тоже теги | типизированные поля `CardData` | **у Card Wars лучше** (типизация, валидация генератором) |
| Статусные флаги | теги на сущности (TAUNT, FROZEN…) | почти нет: `flipped`, `frozen` только у земель | **заимствовать** (§6, R1) |
| Баффы | отдельные сущности-зачарования с id/источником/зоной | `bonusAttack/bonusDefense` + `TurnBuff[]` без id и источника | **заимствовать идею** (§6, R2) |
| Ауры | сущности, периодически тикают, пересоздают зачарования | пересчёт в точке использования, ничего не хранится | у Card Wars проще; ок для текущих масштабов |
| Триггеры | зачарование-сущность с данными триггера | очередь `QueuedAbility` в фрейме | эквивалент по смыслу, у HS — через сущности |
| Смерти | отдельная фаза Death Processing | `deaths.ts` | сопоставимо |
| Репликация | поток элементарных дельт (`TAG_CHANGE`…), один формат для игры/лога/реплея | полные персональные снапшоты + события только для анимаций | осознанное упрощение Card Wars; **не менять**, но атомизировать события (§6, R3) |
| Легальность розыгрыша | PlayReq — данные | валидация в `play.ts` кодом | заимствовать подход при появлении карт с условиями розыгрыша (§6, R4) |
| Сложные карты | спецкод в движке по карточному ID | именованные механики в реестре (`registry.ts`) | **у Card Wars чище** (реестр механик — не карта, конвенция №2 соблюдается строже, чем у Blizzard) |

### 5.3 Ответ на исходный вопрос про «как берутся карты»

- В Hearthstone карта «берётся» дважды: определение — из файлов данных клиента (`CardDefs`), состояние — теги сущности в матче. Сложные эффекты — код в движке по ID.
- В Card Wars: определение — из `content/` через генератор в `packages/content`, состояние — `CardInstance` в `MatchState`. Эффекты — интерпретатор DSL из данных; сложные — реестр именованных механик.
- Обе системы **не хранят копию определения в состоянии** и **вычисляют эффективные статы** (HS: property с баффами; CW: `computeEff` с аурами). Разница принципиальна в одном: у HS каждый бафф — наблюдаемая сущность, у CW бафф — безымянная запись.

## 6. Рекомендации

### 6.1 Заимствовать

**R1. Теги-статусы на `CardInstance`.**
Сейчас для нового статусного эффекта («существо нельзя атаковать», «оглушено») пришлось бы плодить булевы поля. HS-решение: один мешок статусов — `tags: Set<CardTag>` (узкий union-тип, не строковый словарь) на инстансе; правила спрашивают `hasTag(inst, 'stunned')`. `frozen` у земель мог бы со временем переехать туда же. Генератор каталога сможет валидировать, что данные карт ссылаются только на известные теги. Компромисс против HS: сохранить типизацию узким union, а не произвольным словарём.

**R2. Идентичность баффов (облегчённые «зачарования»).**
`TurnBuff = {instanceId, stat, amount, grantedOnTurn}` (`types.ts:112`) — нет ни источника, ни id. Для кейсов «когда источник умирает/уходит — снять его баффы», стаков и отладки нужны `buffId` + `sourceInstanceId` + `abilityId` (и аналогично для перманентных `bonusAttack/bonusDefense` — либо их мигрировать в тот же механизм). **Не** превращать баффы в полноценные сущности, как в HS: пересчётный механизм аур у Card Wars работает и для 2–4 игроков дешевле.

**R3. Атомарные события презентации (аналог TAG_CHANGE).**
Сделать события анимаций элементарными — `{instanceId, поле, было → стало}` — вместо составных. Клиент склеивает анимации сам; попутно бесплатно появляется журнал матча/реплей. Полные снапшоты не трогать: гибрид «снапшот + атомарные дельты для презентации» — развитие текущего TECH.md, а не ломка.

**R4. Требования розыгрыша как данные (PlayReq-подход).**
Если появятся карты с условиями розыгрыша («нельзя играть, если на поле > N существ»), описывать требования массивом данных в `AbilitySpec`/определении и валидировать универсальным автоматом, а не кодом на карту.

### 6.2 Не заимствовать

- **Мешок тегов на всё** (как у HS): потеря типизации строгого domain; издержки сериализации в DO/SQLite не оправданы при 544 картах и известном наборе полей.
- **Спецкод на карту**: запрещён конвенцией №2; реестр именованных механик — лучшая альтернатива (код механики, не карты).
- **Поток дельт вместо снапшотов**: неоправданная сложность протокола при 2–4 игроках; HS платит за неё реплеями и масштабом.

### 6.3 Когда пересмотреть

- Рост числа статус-эффектов и взаимодействий «пока X — Y» → приоритет R1 повышается.
- Потребность в реплеях/журнале для отладки споров → R3.
- Появление перманентных баффов от других карт → R2.
- Появление карт, меняющих правила хода (у HS для этого тоже энчантменты) → сначала расширить `ConditionSpec`, только потом R2/R4.
