# Архитектура (высокоуровневая)

## Главная идея

Игра строится как **чистый игровой движок + тонкие адаптеры**.

```
┌─────────────────────────────────────────────────────┐
│                    Presentation                      │
│         (UI, 2D/3D, ввод пользователя)               │
└──────────────────────┬──────────────────────────────┘
                       │ команды / события
┌──────────────────────▼──────────────────────────────┐
│                  Application                         │
│     (use-cases: начать матч, сыграть карту,          │
│      закончить ход, сохранить реплей…)               │
└──────────────────────┬──────────────────────────────┘
                       │
┌──────────────────────▼──────────────────────────────┐
│                     Domain                           │
│  • Модели (Card, Player, Zone, Match…)               │
│  • Правила и валидация                               │
│  • State machine хода                                │
│  • Применение эффектов                               │
│  • Чистые функции перехода состояния                 │
└─────────────────────────────────────────────────────┘
                       ▲
                       │ порты
┌──────────────────────┴──────────────────────────────┐
│                   Adapters                           │
│  • Persistence (колоды, реплеи)                      │
│  • Multiplayer transport                             │
│  • Clock / RNG                                       │
└─────────────────────────────────────────────────────┘
```

Domain **ничего не знает** о React, Three.js, Supabase, WebSocket и т.д.

---

## Слои подробнее

### 1. Domain (ядро)

Ответственность:
- Описание всех игровых сущностей.
- Валидация действий («можно ли сейчас сыграть эту карту»).
- Переходы состояния матча.
- Расчёт урона, флюпов, замен существ, розыгрыша заклинаний.
- Определение победителя.

Характеристики:
- Чистые функции или методы без побочных эффектов (кроме явно переданного RNG).
- Полностью покрыто unit-тестами.
- Можно запустить в Node без DOM и браузера.

### 2. Application

Оркестрирует сценарии:
- «Создать новый матч из двух колод»
- «Игрок хочет сыграть карту»
- «Игрок заканчивает ход»
- «Запросить возможный муллиган»

Не содержит правил «как считается урон», только вызывает domain.

### 3. Presentation

- Отображает текущее состояние матча.
- Собирает намерения пользователя и передаёт их в application в виде команд.
- Не решает, законно ли действие.
- На старте — максимально простой UI (можно даже текстовый или примитивный 2D).

### 4. Adapters

Всё, что касается внешнего мира:
- Загрузка/сохранение колод.
- Мультиплеер (когда появится).
- Генерация случайных чисел (чтобы тесты были детерминированными).
- Логирование, аналитика и т.п.

## Состояние матча

Состояние — **единый иммутабельный снимок**.

Любое действие игрока = команда → domain проверяет → возвращает новый снимок (или ошибку).

Рекомендуемый подход к ходу — **явный state machine** фаз, например:

```
Setup → Draw → Main (действия / флюпы) → Combat → EndTurn → (переход к другому игроку)
```

Конкретные названия фаз будут уточнены в правилах. Важно, чтобы фаза была частью состояния и ограничивала доступные команды.

---

## Карты и эффекты

Карты описываются данными (id, тип, стоимость, требования к землям, атака/защита, текст).

Эффекты реализуются как:
- либо декларативные операции (нанести N урона, добрать карту, уничтожить…),
- либо именованные обработчики для сложных случаев.

UI не должен содержать логику «что делает эта карта».

---

## Чего намеренно избегаем (в отличие от текущей кодовой базы)

- Игровой state, размазанный по React-компонентам и Zustand «на всё».
- 3D-сцена как часть ядра игры.
- Оптимистичные патчи и сложная синхронизация на самых ранних этапах.
- Привязка правил к конкретной базе данных или realtime-каналу.
- Большой монолитный «gameStore», который одновременно знает про сеть, UI и правила.

---

## Эволюция

1. **Сейчас** — только domain + тесты + самый простой способ «поиграть» (даже CLI или минимальный UI).
2. Потом — нормальный 2D-интерфейс.
3. Потом — сохранение колод, реплеи.
4. Потом — мультиплеер как адаптер.
5. Потом (если нужно) — 3D-представление как ещё один presentation-адаптер.
