## 06:14 — Продолжение механики Газы Огрa
<!-- начато 2026-11-03 06:14:21 +03:00 (Europe/Moscow) -->

### Задача
Продолжить незавершённое внедрение механики «Газы Огрa»: публичное вскрытие 3 карт, выбор одной карты вниз колоды, две остальные в сброс, ввод через pendingChoice без обхода серверной валидации.

### Сделано
- Domain: добавлены операции `reveal_deck_top` и `resolve_revealed`, последовательные эффекты с ленивым сбором выборов (`effect_step`), постановка и возобновление через `resolve_choice`; добавлен `discard_from_hand` с неявными выборами.
- Состояние/матч: `MatchState.revealed` публикует только текущее окно до подтверждения/отмены; `time_expired` и отсутствующий источник очищают окно без перемещения вскрытых карт.
- Розыгрыш: способности `on_cast` ставятся в trigger queue с pre-collected target choices, поэтому несколько способностей нормально продолжаются после pause; прямые non-array эффекты применяются атомарно до drain.
- Протокол/виды/UI: `RevealedCardView`, поле `revealed` в `PlayerView`, `PendingChoiceView.kind='effect_step'`; HUD показывает открытые карты и кнопки выбора владельцу, зрителю — только имена. Серверная валидация остаётся единственным авторитетом.
- Каталог/тесты: новый mechanics JSON `content/cards/mechanics/bmo_card_4.json`; golden-тест успешного розыгрыша и timer-cancel; unit-тест переноса вскрытия в `viewFor`; журнал и docs (`MECHANICS-V2.md`, `COMMANDS.md`) обновлены.

### Проверки
- `pnpm --filter @card-wars/content generate` → 544 cards, 25 heroes, mechanics cards 150/544, heroes 8/25.
- `pnpm -r test` → protocol 4/4, domain 95/95, content 27/27, application 5/5, server 15/15 — зелёные.
- `pnpm -r build` → успешно; обычные предупреждения Vite о размере чанка/комментариях zod, новых ошибок нет.

### Решения
- Вскрытие карт является публичной информацией, поэтому участвует в обеих персональных вида и событиях; чужие руки/колода по-прежнему не передаются клиенту.
- Интерактивные массивы не требуют TargetChoice заранее; движок спрашивает следующий `TargetAsk` только когда effect действительно требует выбор. Это исключает команду с угаданными целями.
- `on_cast` переведён на общий trigger queue вместо прямого выполнения, чтобы pause корректно сохранял очередь и следующие способности не исполнялись до ответа.
- Клиент лишь отправляет выбор; легальность, порядок, область и перемещение карточек проверяет domain.

### Находки и риски
- `pnpm -r build` ранее был выполнен до финальной правки журналов/тестов; после правок build повторён и успешен.
- Публичное раскрытие неизбежно видно обоим партнёрам/противникам по правилам этой способности; это не утечка руки/колоды, остаток колоды не раскрывается.
- 3D/HUD не показывает изображения открытых карт, только имена и выбор; анимация раскрытия не реализована.
- Изменения не закоммичены и продолжают ранее существовавшую незакоммиченную механику.

## 11:24 — Разблокировка хода в комнате 0472 (бот на pendingChoice)
<!-- начато 2026-11-03 11:24:22 +03:00 (Europe/Moscow) -->

### Задача
В живой комнате 0472 (wrangler dev, DO Room) ход застрял на боте и не передавался; нужно быстро отдать ход пользователю, разбор бага — потом.

### Сделано
- Диагноз: прямой SQL-доступ к хранилищу DO закрыт (`_cf_KV` — SQLITE_AUTH через Explorer), WS-имперсонация невозможна (`handleCommand` проверяет `command.player === attachment.playerId`, за бота команды не принимает). Штатный таймер хода у бота не тикает: таймеры в `timer.ts` стартуют только по «Поторопить» (`hurry`), авто-истечения нет.
- Корневая цепочка бага: `apps/server/src/room.ts` → `performBotAction` шлёт обычную команду / fallback `go_battle`; при открытой `match.pending` (docs/MECHANICS-V2.md §6) обе отклоняются доменом с `choice_pending` (`packages/domain/src/match/apply.ts:144-152`), `performBotAction` возвращает `false`, а `scheduleBots` снова планирует то же действие → вечный цикл, ход не передаётся.
- Фикс (минимальный, `apps/server/src/room.ts`): в `performBotAction` — если владелец `match.pending` — бот, бот отвечает командой `time_expired` (детерминированный дефолт таймера: skip/cancel выбора + авто «В бой», apply.ts case `time_expired`); обычный обход активных игроков при открытом pending пропускается. Отдельного юнит-теста на сценарий пока нет — в планах.

### Проверки
- `pnpm --filter @card-wars/server test` → 15/15 (timer 7, deck 5, bot 3) зелёные.
- Explorer API: `GET .../workers/durable_objects/namespaces` → namespace `card-wars-Room` (sqlite); объект `0472` = `1eac6da2cd1d53634a2ba56e1ca67e80c661a81ba7cbd5c961d6989719495a9e`; SQL к `_cf_KV` запрещён (код 10001).

### Решения
- Отброшено: патч состояния через SQL DO (запрещён + кэш `state` в памяти DO), подмена/реконнект за бота (валидация сессии). Перезапуск wrangler не помог бы — состояние воспроизводится.
- `time_expired` выбран потому, что уже является легальным ответом по истечении таймера хода (тот же дефолт) — никакой новой логики в domain не добавлялось (чистота domain сохранена).

### Находки и риски
- Если pending принадлежит не боту, а живому игроку, и бот при этом должен действовать — цикл отказов сохраняется (не чинил, вне скоупа быстрого разблокирования).
- Правка подхватывается живым wrangler dev автоматически; состояние комнаты в DO переживает reload (version 1), токены сессий сохраняются.
