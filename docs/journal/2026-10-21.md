## 03:40 — Роутер AX3000T: причины «интернет пропадает на пару секунд» и правки
<!-- Метка времени: 2026-10-21 03:40:16 +03:00 (Europe/Moscow) -->

### Задача
Найти причину периодических обрывов интернета по Wi-Fi на Xiaomi AX3000T RD03v2 (OpenWrt v2.0.1,
kernel 6.18.55, AmneziaWG + сплит-туннель), устранить и оптимизировать.

### Сделано
- Полный аудит исключил локальные причины: uplink 5 ГГц (−51 dBm, 160 МГц, 2401/2161 Мбит/с,
  `tx retries 0`, `tx failed 0`, `beacon loss 0`), потери до шлюза 0 % при 3.4 мс, UDP-стек без
  дропов (`InErrors 0`), conntrack 63/11264, память 33 МБ свободно, swap не используется,
  `CTRL-EVENT-DISCONNECTED` = 0, hostapd не перезапускается, flow offload и NSS offload выключены.
- Локализовано: потери возникают на стороне сервера AmneziaWG — 30–90 % чёрными провалами
  по 10–20 с при 0 % потерь на ICMP до того же IP; `ifdown awg; ifup awg` возвращает 0 %.
- Написан сторож `/usr/sbin/pgate-tunnel-watchdog` + `/etc/init.d/pgate-tunnel` (procd, автозапуск):
  пинг 1.1.1.1 и 8.8.8.8 по 5 пакетов каждые ~40 с; при 100 % на обеих целях немедленный
  перезапуск интерфейса, иначе после 2 плохих замеров; после 3 неудач — переключение на
  `/etc/pgate-fallback.conf` (US_54) и обратно на `/etc/pgate-primary.conf` (US_23).
  Журнал `/overlay/pgate-tunnel.log`, ротация 5000 строк, отключение через `/etc/pgate-tunnel.disable`.
- Исправлен IPv6: `filter_aaaa=1`, `ra/dhcpv6/ndp=disabled`, из `network.awg.dns` убран мёртвый
  `2a07:b944::2:1`. Причина: AAAA отдавались, а IPv6 наружу не работал (`ping -6 2a07:b944::2:1` —
  100 % потерь) → телефон сначала шёл по IPv6 и ждал таймаут.
- Добавлен MSS-клэмпинг для туннеля (в `/etc/nftables.d/10-pgate-split.nft` цепочка `pgate_forward`,
  `oifname "awg" ... maxseg size set rt mtu`): MTU awg 1420 против LAN 1500, без клэмпинга
  фрагментация и «страница загрузилась и замерла».
- 2.4 ГГц AP: `disassoc_low_ack=0` (hostapd выкидывал клиентов по низкому ACK), `txpower 30 → 20 dBm`.
- Проверено: `type route` в этом ядре не поддерживается (нет `nft_chain_route_ipv4`), `veth` тоже —
  поэтому собственный трафик роутера сплит не покрывает (для пересылаемого трафика с LAN метка
  работает: маршрут выбирается после prerouting). Задокументировано как ограничение.
- Замеры скорости через туннель: US_23 0.36–0.63 МБ/с, US_54 0.42–0.62, US_78 0.46, US_30 1.21
  (занят ноутбуком, тот же приватный ключ — конфликт endpoint, на роутер не ставим). Все 0 % потерь,
  потолок провайдера. Оставлены US_23 (основной) и US_54 (резерв).

### Проверки
- `ping -c 10 1.1.1.1` → 0 % потерь, 184 мс; `http://api.ipify.org` → 149.40.62.44.
- `nslookup ya.ru 127.0.0.1` → только A-записи; DNS 0.01–0.09 с.
- `nft list chain inet fw4 pgate_forward` → правило MSS на месте; три цепочки `pgate_*`.
- `iw dev phy0-ap0 info` → `txpower 20.00 dBm`; `iw dev phy1-sta0 station dump` → retries/failed 0.
- `/etc/init.d/pgate-tunnel enabled` → да; процессов сторожа 1; в журнале были срабатывания
  на 100 % потерях во время ручных переключений профилей (ожидаемо).

### Решения
- Не трогать рабочую схему сплита (nft set + fwmark + `ip rule`), она рабочая; правки минимальные.
- Не ставить US_30 на роутер: совпадает с профилем ноутбука (один приватный ключ), сервер будет
  перекидывать endpoint между устройствами.
- Канал 2.4 ГГц оставлен ch1 (33 % занятости): смена без клиента для проверки — гадание.

### Находки и риски
- Провайдер/сервер даёт 0.4–0.6 МБ/с на US-профилях — это не роутер.
- `dmesg`: `ath11k tx completion mismatch count ... ring id 0` ~1/мин на 5 ГГц радио — баг драйвера,
  потерь не даёт (retries 0, ICMP до шлюза чистый). Оставлено как известное.
- Телефон `Redmi-Note-10S` (192.168.1.115) к AP не подключён — end-to-end на реальном клиенте
  не проверен.
