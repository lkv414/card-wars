# TECH.md — Технические решения (v3)

## Назначение и статус

Документ фиксирует **технологии и технические решения** реализации v3. Игровые документы (PROJECT, ARCHITECTURE, RULES, CARDS, …) остаются нейтральными к технологиям ([README.md](./README.md), принцип 5) — стек фиксируется **только здесь**.

- Меняется техническое решение → меняется этот документ.
- Меняется правило игры → меняются игровые документы, этот следует за ними.
- Решения приняты по итогам обсуждения (октябрь 2026) и согласованы с владельцем проекта.

## Структура репозитория

```
docs/                    — игровая и техническая документация
packages/
  domain/                — ядро правил + unit-тесты            (STRUCTURE.md: domain)
  application/           — use-cases, журнал, viewFor          (STRUCTURE.md: application)
  protocol/              — схемы и типы команд/событий/снимков (zod), CONFIG
  content/               — каталог карт, герои, пресеты колод MVP, изображения
apps/
  server/                — Worker: Room (DO), транспорт, боты, static assets
  client/                — React-приложение (presentation + клиентские adapters)
```

### Правила зависимостей

- `domain` → ничего (единственное исключение — Immer, см. «Отклонения»).
- `application` → `domain`, `protocol`, `content`.
- `protocol` → только zod.
- `content` → `domain` **только типами** (формат карты/каталога описан в domain; данных и кода из domain content не использует).
- `server` → `domain`, `application`, `protocol`, `content`.
- `client` → `protocol`, `content`. Напрямую `domain`/`application` клиент **не использует**: роль application на клиенте выполняет сетевой адаптер (отправка команд, приём снапшота) — это отображение правила «presentation зависит от application» ([STRUCTURE.md](./STRUCTURE.md)) на клиент-серверное разделение.

### Сборка и деплой

- `pnpm -r build`: content/protocol/domain/application → client (Vite → `dist`) → `wrangler deploy` из `apps/server`. Конфиг wrangler: `assets.directory = ../client/dist`, DO-миграция `new_sqlite_classes`.
- Локально: `wrangler dev` поднимает Worker + DO (Miniflare); клиент раздаётся тем же dev-сервером.

## Сервер

### Топология

- Один Worker обслуживает: static assets (клиент), `GET /health`, WS-эндпоинт `/ws`.
- Один DO-класс **`Room`**: имя объекта = код комнаты. Комната живёт от создания до завершения/распада партии; внутри — упрощённое лобби (MVP) и состояние матча.
- Однопоточность DO гарантирует отсутствие гонок при применении команд — дополнительная синхронизация не нужна.

### Жизненный цикл состояния

1. Состояние матча держится в памяти Room; **после каждой** применённой команды новый снапшот и прирост журнала пишутся в SQLite-хранилище DO (write-through).
2. Hibernation/выселение инстанса не теряет партию: при пробуждении Room читает состояние из storage. Это надёжнее «всё в памяти» на обычном сервере.
3. Персональный вид — 5–20 КБ JSON; лимит значения в SQLite-DO — 2 МБ: запас достаточен.

### Подключение и реконнект

- Клиент открывает WS и шлёт `join {code, nickname, token?}`.
- Комнаты нет → Room создаётся, отправитель становится **хостом**. Комната есть → игрок занимает свободный слот.
- `token` совпал с существующей сессией → **реконнект**: старое соединение закрывается, клиенту повторно отправляется снапшот.
- Токен — случайная строка, выдаётся при первом входе, хранится в `sessionStorage` (на вкладку/устройство).
- Обрыв WS → партия на паузу, alarm через `reconnectWaitSeconds` (60 с) от **первого** оборвавшегося ([NETWORK.md](./NETWORK.md)). Вернулся по токену — пауза снимается; не вернулся — партия завершается поражением обрывавшемуся (в 2 на 2 — команде).
- Heartbeat ping каждые 30 с для быстрого обнаружения мёртвых соединений.

### Таймеры (alarms DO)

- Таймер хода — стейт-машина **в адаптере** ([STRUCTURE.md](./STRUCTURE.md): domain получает только команду «время вышло»): `{baseRemainingMs, lastResumedAt, speedupUntilAt}`. По дедлайну Room ставит alarm и применяет автоматическую команду `TurnTimerExpired`.
- «Поторопить» пересчитывает оставшееся время с окном ускорения ×2 на 1 с (спам перезапускает окно, быстрее ×2 никогда — [RULES.md](./RULES.md)) и перевыставляет alarm. Стейт-машина таймера покрыта unit-тестами отдельно.
- Клиентам после каждого события рассылается `{remainingMs, serverNowMs}` — клиент только рисует отсчёт, не считает.

### Боты

- Бот — код внутри Room; после каждого перехода хода, если активен бот, Room вычисляет команду (эвристика v1: оценка размена, агрессия) и применяет через тот же application-API, что и живые игроки. Для клиентов бот неотличим от игрока ([NETWORK.md](./NETWORK.md), «Боты»).
- CPU-лимит инвокации на Free-плане (10 мс) — с большим запасом для эвристик.

## Этап 5 — лобби, мультиплеер, боты, редактор (реализация)

Решения этапа (дополняют игровые документы, не заменяют их):

- **Domain:** матч знает режим (`ffa` / `teams`) и вариант команд (`neighbors` / `wall`). В 2 на 2 у команды общие жизни, ход команды ведут оба союзника (`activePlayers`), у каждого своя готовность к бою. Сопоставление зон с противником — одна функция: FFA/«соседи» — зоны 1–2 против левого живого соседа, 3–4 против правого, зеркально; «стенка» — сквозная нумерация 8 зон и зеркало `9 − N`. Парные карты играбельны только в 2 на 2.
- **Сервер:** Room — полноценная машина лобби (слоты, готовность, режим, скрытие, боты, пересадка, кик, передача хоста). Колоды проверяются сервером по каталогу и CONFIG при выборе и на старте. Боты принимают решения по своему `viewFor` и действуют через `applyCommand` с задержкой; очередь ботов и таймеры живут в alarms. В 2 на 2 — отдельный таймер на каждого активного союзника. Смоуки: `smoke` (лобби + партия) и `smoke:bots` (2 на 2 с тремя серверными ботами).
- **Клиент:** главное меню, список колод и редактор — DOM; лобби — DOM; игровой экран — 3D. Колоды хранятся в localStorage, код колоды — `{v, hero, lands[4], cards[40]}` → base64url + crc32. В лобби доступно быстрое редактирование колоды.
- **Редактор колод:** фильтры по типу/стоимости/земле и избранному, лимит 4 копии, ровно 40 карт, 4 земли, герой; парные карты скрыты по умолчанию и показываются в режиме 2 на 2.
- **Сцена:** мой ряд всегда внизу; 3–4 игрока — доски вокруг стола (мой ряд снизу, соседи по часовой); 2 на 2 «соседи» — квадрат с союзником напротив; «стенка» — два ряда по 8 зон. Анимации и жетоны считают мировые позиции через трансформацию доски.
- **Мобильные:** одна колонка на списочных экранах, компактный HUD, тач через pointer events, камера с адаптивным FOV; полного орбитального управления нет.

Решения по продукту (приняты консервативно, зафиксированы в документах): отдельного списка комнат нет; команды 2 на 2 выводятся из посадки; в 2 на 2 первый круг — без флюпов и атак; первая сдача в 2 на 2 фиксируется, команда выбывает после второй; способности парных карт пока остаются текстом (как и остальной контент, ждут нового OCR).

## Протокол

| Направление | Сообщение | Содержание |
|-------------|-----------|------------|
| C→S | `join` | код, ник, токен, `protocolVersion` |
| C→S | `lobby_command` | готовность, колода, режим, скрытие, боты, пересадка, кик, передача хоста, старт, выход |
| C→S | `command` | команда из каталога [COMMANDS.md](./COMMANDS.md) |
| C→S | `hurry` | игрок-адресат (активный таймер; в 2 на 2 — конкретный союзник) |
| S→C | `joined` / `lobby` | персональный id/токен, состояние лобби (слоты, режим, готовность) |
| S→C | `snapshot` | полный персональный вид (включая журнал) |
| S→C | `events` | события последнего применения команды |
| S→C | `error` | причина отклонения команды |
| S→C | `timer` | оставшееся время по каждому активному игроку + `serverNowMs` |

- Формат — JSON UTF-8; `protocolVersion` проверяется при `join`.
- **Снапшот — источник истины**: клиент заменяет свой вид целиком; ошибки не накапливаются, реконнект = повторная отправка снапшота. Состояние крошечное (десятки объектов), поэтому дельты не нужны.
- **События не мутируют состояние** — только анимации, подсветки, журнал.
- **Скрытие информации**: снапшот строит только `viewFor(state, playerId)` (application); события не содержат скрытых данных (чужие руки, колоды). Персональные события будущего (`peek` и т.п.) отправляются только адресату.
- Схемы zod в `packages/protocol`; TS-типы выводятся из схем (`z.infer`) — единый контракт клиента и сервера.
- Журнал: строки формата [RULES.md](./RULES.md) собираются на сервере из событий и передаются в составе снапшота; экспорт .txt — на клиенте. На старте журнал передаётся целиком; при росте — окно + дозагрузка.

## Domain / application — правила реализации

- `applyCommand(state, command, deps) → {state, events} | reject` — чистая функция; `deps = {rng, config}`.
- RNG — порт; детерминированный сидированный PRNG, сид хранится в состоянии матча (воспроизводимость партии по журналу). В тестах — фиксированный сид.
- CONFIG — объект со значениями из [CONFIG.md](./CONFIG.md), передаётся в domain; констант-дублей в коде правил нет.
- `viewFor(state, playerId)` в application — **единственное** место построения персонального вида; обязательный тест «чужая рука/колода нигде не встречаются в JSON».
- Property-based тесты (fast-check): зеркальное сопоставление зон, перестройка направлений боя при выбывании, инварианты состояния.
- Тестовое покрытие domain — [MVP.md](./MVP.md), раздел «Тесты».

## Контент

- `packages/content`: каталог собирается из папки [`content/`](../content) скриптом `tools/build-catalog.mjs` (`pnpm --filter @card-wars/content generate` → `src/generated/*.json`, файлы коммитятся). `content/` — источник правды: по JSON на карту/героя, картинки рядом, общий `index.json`. Правки `generated/*.json` вручную не делаются.
- **Каталог:** 545 уникальных карт (из 840 сканов), 25 героев; типы — `creature`/`spell`/`building`/`companion`, земли — восемь значений включая `ghost` (2v2). Способности карт пока текстовые (`abilities: []`) — структуризация следующий этап.
- **Автоматические триггеры и цели:** если пассивный триггер (on_death, start_of_turn) требует выбранную цель, эффект пропускается — спросить игрока в этот момент нельзя; `on_enters_play` получает `choices` из команды розыгрыша. Это осознанное ограничение v1.
- **Герои**: источник имён/текстов — `content/heroes/`; структурированные эффекты по документации (RULES.md): **БиМО** — доп. добор, **Билли** — победа при пустой колоде всех противников (операция domain `win_if_opponents_deck_empty`). Остальные 23 героя — текст-заглушки.
- **Пресеты колод MVP** (этап 3, готово): Бимо — тема `blue`, Билли — тема `good`; детерминированный сборщик `buildPreset` (6 существ + 2 строения + 2 заклинания × 4 копии, земли: тема×3 + радуга).
- **Арты — гибрид**: на старте canvas-фреймы, генерируемые из данных карты (быстрый старт, без зависимости от файлов); сканы/изображения позже просто подставляются в `content` — код не меняется.
- Каталог **вшит в проект** — версионируется вместе с кодом, доступен и клиенту, и серверу, не требует чтений из хранилища. KV/R2/DO-хранилище под каталог не используется.
- Следить за бюджетом бандла (static assets: до 20 000 файлов, 25 МБ на файл — с запасом).

## Поток подключения (лобби этапа 5)

1. Игрок открывает `https://<домен>/play/1234` (из меню «Присоединиться по коду» или по ссылке).
2. Комнаты нет → создаётся, вошедший — **хост**. Лобби (DOM): код, ссылка, slots, выбор колоды, готовность.
3. Игроки (и боты, добавленные хостом) занимают слоты; хост настраивает режим и скрытие, пересаживает участников.
4. Все готовы → хост нажимает **«Начать»** → матч; в 2 на 2 команды определяются посадкой.
5. Колоды участников — выбранные в лобби (по умолчанию пресеты), проверены сервером.

## Процесс

- **AGENTS.md** в корне — всегда загружаемые инструкции агента (clean-room, конвенции, команды). Скиллы проекта в `.agents/skills/`: `ask-first` (уточнять, а не догадываться — адаптация `interview-me` из addyosmani/agent-skills), `card-review` (ревью по чеклисту проекта). По мере этапов: `match-sim`, `add-card`, `add-mechanic`, `dev-run`, `deploy`.
- **MCP**: подключены к workspace — `context7` (актуальные доки библиотек), `cloudflare-docs` (документация Workers/DO), `cloudflare-observability` (логи/аналитика аккаунта; при первом использовании — OAuth-вход в Cloudflare), `cloudflare` (единый официальный сервер, OAuth при первом обращении). Вход для **деплоя** — не MCP, а `wrangler login` (браузер, один раз) либо API-токен в переменных окружения. Установлены официальные скиллы Cloudflare (`~/.agents/skills/`: wrangler, durable-objects, workers-best-practices и др.) и бета-CLI `cf` (полное покрытие Cloudflare API; в этом проекте приоритет — wrangler, т.к. есть wrangler.jsonc).
- **Дизайн** — code-first: макеты описаны в docs и собираются сразу в коде. Figma MCP (чтение макетов) отложен; обратной синхронизации «код → Figma» из коробки нет — если появится макет, изменения вносит владелец.
- **Язык кода**: идентификаторы и комментарии — английский, строки интерфейса и игровой контент — русский.

## Лимиты и эксплуатация

- Free-план Workers: ~100 000 запросов/день; DO — только SQLite-backed; hibernation — простой не тарифицируется; CPU 10 мс/инвокация. При росте — Workers Paid ($5/мес).
- Наблюдаемость: `wrangler tail`, логи DO; алерты на старте не настраиваются.
- Риски: vendor lock-in Cloudflare (смягчён портами — перенос на Node = один адаптер); учёт WS-сообщений в квоте (следить при росте); вес артов (бюджет бандла).
