# Card Wars — Описание проекта (v3)

## Что это

Цифровая реализация настольной карточной игры **Card Wars** (из вселенной Adventure Time).

Два игрока сражаются колодами существ, строений и заклинаний на поле из четырёх зон. Цель — снизить жизни соперника с 25 до 0.

Проект — **не** клон текущего репозитория. Это новая реализация, созданная по спецификации.

---

## Цели проекта

1. **Корректная игровая логика**  
   Правила должны быть реализованы точно и проверяемо. Логика игры существует отдельно от интерфейса.

2. **Чистая архитектура**  
   Жёсткое разделение:
   - правила и состояние матча (domain)
   - сценарии использования (application)
   - UI, сеть, хранение (adapters)

3. **Понятность**  
   Новый разработчик (или будущий ты) должен быстро понять, где что находится и как добавить новую карту/механику.

4. **Инкрементальность**  
   Можно играть локально (два игрока за одним экраном или vs простой ИИ) ещё до появления сети и красивого интерфейса.

---

## Что проект НЕ делает (на старте)

- Не стремится сразу к 3D-доске и сложной графике.
- Не завязан на конкретный BaaS (Supabase и т.п.) как на ядро.
- Не смешивает UI-состояние с игровым состоянием.
- Не пытается сразу покрыть все возможные наборы карт и все edge-cases оригинала.

---

## Основные сущности (высокоуровнево)

- **Карта** — существо, строение или заклинание. Имеет стоимость, тип земель, текст эффекта.
- **Земля (Land)** — определяет, какие карты можно разыгрывать. У каждого игрока 4 земли.
- **Зона** — пара противостоящих земель (своя + чужая). На поле 4 зоны.
- **Игрок** — колода, рука, сброс, жизни (25), контролируемые карты и земли.
- **Матч (Game)** — полное состояние партии + текущая фаза хода.
- **Действие** — единица ресурса на ход (обычно 2 за ход).
- **Флюп** — специальная активация карты (поворот + эффект).

---

## Принципы, которым должна следовать реализация

1. **Domain First**  
   Сначала чистый движок правил (без React, без сети, без БД). Его можно тестировать unit-тестами и запускать в Node.

2. **Явная модель состояния**  
   Состояние матча — иммутабельная структура. Переходы только через определённые команды/события.

3. **Правила как данные + код**  
   Карты и эффекты описываются декларативно насколько возможно. Сложная логика — в отдельных обработчиках, а не размазана по UI.

4. **UI — тонкий слой**  
   Интерфейс только отображает состояние и отправляет намерения («сыграть карту X в зону Y»). Он не решает, законен ли ход.

5. **Сеть — опциональный адаптер**  
   Мультиплеер появляется после того, как локальная игра стабильна. Транспорт (WebSocket, Supabase Realtime, что угодно) — деталь реализации адаптера.

## Технологический стек (рекомендация, не догма)

Документация **не диктует** конкретные библиотеки.  
Рекомендуемый ориентир для реализации:

| Слой              | Рекомендация                          | Почему |
|-------------------|---------------------------------------|--------|
| Язык              | TypeScript                            | Типы помогают моделировать правила |
| Domain            | Чистый TS, без фреймворков            | Тестируемость и переносимость |
| UI (позже)        | React или аналог                      | Привычный и достаточный |
| State UI          | Любой (Zustand, Redux, signals…)      | Не важен, пока domain чистый |
| Рендер доски      | Сначала 2D/CSS, 3D — опционально позже| Избежать ранней сложности |
| Тесты             | Vitest / Node test                    | Обязательны для domain |

Стек можно менять, **слои и границы — нет**.
